## 2. View-dependent portal proof

The native `viewpoint-demo` successfully showed depth-dependent head-motion parallax on a Quest 3.
It is an ordinary Wayland full-SBS client; HypXRland remains the OpenXR session owner. The client
declares the xdg tag `stereo:sbs`, but the user's active stereo policy matched the distinct ordinary
Hyprland tag `stereo-sbs`. The successful live sequence therefore included:

```sh
# With the persistent viewpoint authorization rule described in doc 10:
hyprctl dispatch tagwindow +stereo-sbs address:0xWINDOW_ADDRESS
```

Before that tag, `hyprctl -j clients` reported `stereo: off` and the packed image looked wrong.
After it, the field resolved to `stereo: sbs`, the protocol activated, samples advanced, rendered
frame hashes changed, and the wearer confirmed the parallax. Use one of doc 10's two stereo-policy
recipes; do not conflate xdg tags with Hyprland tags.

Moving the monitor deliberately deactivates viewpoint feedback during the grab/carry. Release
should produce a new activation epoch and resume samples automatically; this happened in the live
proof. A static image during the move is expected. A static image after release requires checking
fullscreen/viewport eligibility, the `stereo` rule result, and `viewpoint on` authorization.

No Wine/Dead Space bridge exists yet. Exact renderer/output-buffer generation attribution,
timestamps/pose-age telemetry, nesting, and game-specific HUD/culling/effect classification also
remain open. The next portal work should start from doc 10's explicit missing-pieces and acceptance
lists rather than redesigning the OpenXR ownership model.

## 4. Quest recorder control

Recorder control no longer requires an attached ADB connection. The matched host carrier and Quest
APK route the command over WiVRn's existing encrypted control connection:

```sh
~/.local/bin/wivrnctl recorder start
# Accept the visible Android system-capture consent prompt in the headset.
~/.local/bin/wivrnctl recorder status
~/.local/bin/wivrnctl recorder stop
```

`start` reaching `waiting for headset consent` means only that the consent Activity launched;
`status` must report `recording` before capture is considered active. Android requires visible
MediaProjection consent for every new recording. The control channel is encrypted and the host
authenticates the headset public key, but the Quest does not pin a long-lived host key; do not call
it mutual authentication.

The recorder-enabled APK and matched XG host binaries were installed, and `wivrn.service` was
restarted. A disconnected-host check correctly returned `no headset is connected`, but no attended
start/consent/record/stop cycle was completed after deployment. That is the first pending recorder
validation. Completed videos stay on the Quest; transfer and device-log inspection remain
**ADB-only**. The owning WiVRn document is
`/home/ajg/code/wivrn-wt-hypxrrecorder/docs/hypxrrecorder-quest3-truth-probe.md`, including the ADB
fallback and truth matrix.

The installed recorder APK recorded at handoff had SHA-256
`b34e4c0e6d417d3c32b3eaa7da8893d94ff6fa00df7089de7607061e174b4790`. Durable predeployment

## 5. HypXRHUD keys overlay

`hypxrhud-keys` is implemented in HypXRHUD rather than as the standalone OpenXR client proposed by
the old screen-key memo. Matched binaries were installed under `~/.local/bin`, and
`hypxrhud.service` was restarted. `hypxrhud-keys.service` is intentionally static, disabled, and
inactive. No live keystroke capture was performed after installation.

The user manager received
`XR_RUNTIME_JSON=/usr/share/openxr/1/openxr_wivrn.json` with `systemctl --user set-environment` for
that login only; no persistent runtime-selection drop-in was installed. With the headset
disconnected, the new daemon owned its D-Bus name but a bounded method call timed out while its main
thread waited in the WiVRn IPC path. Private-bus tests passed, but do not call the live producer
validated until a connected headset makes the daemon responsive and the panel is visibly submitted.

For the safest attended demo, connect the headset, confirm HypXRHUD is presenting, then start the
producer manually:

```sh
~/.local/bin/hypxrhud-keys --mods-only --verbose
```

The disclosure panel (shown as `KEY DISPLAY ON  -  SHORTCUTS ONLY` in this mode) must keep the same
numeric panel ID and be included continuously in successful XR layer submissions before and during
capture. A queued, dropped, hidden, or `shouldRender=false` panel does
not pass the gate; loss of the panel/runtime/D-Bus owner terminates the exact tracked
`/usr/bin/showmethekey-cli` child. `--mods-only` is strongly preferred for filming, and there is no
automatic password-field masking. The authoritative implementation documentation is
`/home/ajg/code/hypxrhud/docs/keys-overlay.md`; the historical HypXRland design and its correction
are [`research/05-xr-screenkey.md`](research/05-xr-screenkey.md).
